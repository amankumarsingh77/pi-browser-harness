## F1 — Every browser tool fails on Windows: `access()` on a named pipe

> **FIXED** in `2ff5459`. Both call sites now share `daemonSocketMayExist(platform, socketPath)`
> in `src/daemon/spawn.ts`, following the precedent the same file already set.
> Tests: `test/util/daemon-socket-test.ts` pins the platform matrix — a `\\.\pipe\…`
> path on `win32` is never judged absent, while POSIX still consults the filesystem.
> **Still unverified on Windows hardware**: the tests pin the platform *branch*, not
> Chrome's behaviour on Windows. One run of any `browser_*` tool on a real Windows
> box is still the only thing that closes this out.
> The gate's own branch could not be tested deterministically — it calls
> `daemonSocketMayExist()` with no arguments, and this machine has a live
> `/tmp/pi-browser-daemon.sock`, so a gate test asserting "handler skipped" passes or
> fails depending on the developer's machine. I dropped that assertion rather than
> ship an environment-dependent test; the gate is covered only through the helper.

**Location** `src/util/tool.ts:143-157` (guard), `src/daemon/protocol.ts:143-146` (the path).

**What breaks.** `registerBrowserTool`'s `execute` gates every tool on
`await access(DAEMON_SOCKET_PATH)`. On Windows `DAEMON_SOCKET_PATH` is
`\\.\pipe\pi-browser-daemon` — a named pipe, which is not a filesystem entry, so
`GetFileAttributesW` (what libuv's `access` resolves to) cannot see it and `access` rejects.
The guard therefore fails for a perfectly healthy daemon and every `browser_*` call returns
`not_connected: "Browser harness not initialized. Run /browser-setup first"`.

The codebase already knows this. `src/daemon/spawn.ts:44-51` skips the identical pre-check
for exactly this reason, with the comment *"Windows named pipes are not filesystem entries —
`access()` always fails there — so skip the pre-check and probe directly."* `tool.ts` is the
same mistake in the one place it is fatal.

**Trigger.** Any `browser_*` tool call on `process.platform === "win32"`, with or without a
running daemon. `browser_setup` and `browser_http_get` still work (`ensureAlive: false`).

**Impact** The harness is non-functional on Windows, and the error message misdirects the user
to a wizard that cannot fix it. Windows is clearly meant to be supported — the code carries
`.cmd` shim handling, `windowsVerbatimArguments`, PowerShell CIM process detection, and
`LOCALAPPDATA` profile paths.

**Severity** crash (total loss of function on one platform).

**Proposed fix.** Replace the `access` pre-check with the platform-correct liveness probe that
already exists: on POSIX keep `access`, on Windows skip straight to `client.ensureAlive()`
(whose transport `connect` already reports `ENOENT` as "Daemon not running"). Factoring the
POSIX-only branch out of `spawn.ts:45-51` into one shared helper would prevent a third copy.

**Observable behaviour change.** Yes, on Windows only: tools start working. On POSIX, none.

**Reproducible in a test?** Yes, but only after extraction. As written the check is inline in
`execute` and reads `process.platform` transitively through a module constant. Extract
`daemonEndpointReachable(): Promise<boolean>` (or pass the path in) and a test can assert that a
`\\.\pipe\…`-shaped path is not rejected on the strength of `access` alone. Asserting the real
Windows behaviour needs Windows.

**Confidence.** High on the mechanism, **unverified on Windows hardware** — I could not run it
here. Corroborated by `spawn.ts`'s own comment, which the earlier work treated as a verified fact.

## F2 — `runOnElement` ignores `exceptionDetails`: a page-side throw is reported as "No element matched"

**Location** `src/domains/form.ts:30-62`; live at `:142` (fill), `:205` (focus), `:290` (select).

> **FIXED** in `77086bb`. `runOnElement` now checks `exceptionDetails` and returns
> `cdp_error` carrying the exception text. Per the ruling, the error is
> distinguishable from both neighbours: `cdp_error` for a throw, `invalid_state`
> "No element matched" for a genuine miss, `invalid_state` "unknown or stale" for a
> bad ref — all three asserted in `test/domains/form-errors-test.ts`, which failed
> first with `invalid_state` for all three tools. The fix deliberately did **not**
> route the ref path through `resolveAndCall`, which would also have silently fixed
> the out-of-scope handle leak (F29).

*Pre-confirmed item — I agree it is real. I do not rate it the single most severe item; see
"Ranking" below.*

**What breaks.** The ref path calls `cdpCall(client, "Runtime.callFunctionOn", …)`. `cdpCall`
(`src/domains/cdp-call.ts:11-13`) only inspects transport success. A CDP command that *succeeds*
while the page function *throws* returns `{ result: {type:"undefined"}, exceptionDetails: {…} }`.
`runOnElement` returns `ok(r.data.result.value)` = `ok(undefined)`; the handler's
`isFillResult(undefined)` is false, so it takes the `res === undefined` branch and reports
`` `No element matched: ${target}` ``.

**Trigger.** Any exception inside `FILL_FN` / `FOCUS_FN` / `SELECT_FN` on the ref path. Concretely:
`SELECT_FN` starts with `arg.wv` — if the argument ever arrives as `undefined` the very first
statement throws; `FILL_FN` calls `el.dispatchEvent`, which throws if a page overrode it or if a
CSP/permissions error surfaces; a cross-origin `contenteditable` focus can throw. Also every
future edit to those function bodies.

**Impact** A **wrong diagnosis**. The agent is told the ref is bad and re-snapshots a ref that was
fine, then loops. The real error text is discarded. Compare `resolveAndCall`
(`form.ts:361-363`), which does check `exceptionDetails` and reports
`` `page function threw: …` `` — the two code paths in the same file disagree.

**Severity** wrong result (misdiagnosis, agent-visible loop).

**Proposed fix.** Check `r.data.exceptionDetails` in `runOnElement` before reading
`result.value` and return `{ kind: "cdp_error", message: \`page function threw: …\` }`. Better:
delete `runOnElement`'s ref branch and route it through `resolveAndCall`, which already checks
`exceptionDetails` *and* releases the object handle (F29).

**Observable behaviour change.** Yes — a previously-mislabelled failure now returns
`cdp_error` with the page's own message.

**Reproducible in a test?** Yes. Needs a fake `BrowserClient` whose `session().call` returns
`ok({ result: { type: "undefined" }, exceptionDetails: { text: "boom" } })`. No such fake exists
yet; the stub transport in `test/cdp/session-call-test.ts` plus a thin client shim gets there.

## F3 — `switchTo` back to a previously-visited tab silently stops collecting console, network, and page events

> **FIXED** in `d10e729`. `enableDomains` is now called on every attach, not only a
> tab's first visit. Tests: `test/cdp/session-switch-test.ts`, which failed first
> with **zero** `.enable` calls on the returned-to tab's new session.

**Location** `src/cdp/session.ts:350-382`, specifically `368-377`.

**What breaks.** `switchTo` calls `attachTo` (`Target.attachToTarget` with `flatten: true`),
which mints a **new** `sessionId` — the code knows this: `:369` says *"Each
Target.attachToTarget produces a new sessionId — update it."* CDP domain enablement is
**per-session**. But `enableDomains(attachedSessionId)` runs only in the `else` branch, i.e. only
the first time a tab is visited. On a revisit the new session is left with `Page`, `DOM`,
`Runtime`, `Network`, `Accessibility`, and `Log` all **disabled**.

**Trigger.** `browser_switch_tab` to A → `browser_switch_tab` to B → `browser_switch_tab` back
to A. From that moment, on tab A: `Runtime.consoleAPICalled`, `Log.entryAdded`, and every
`Network.*` event stop arriving, so `browser_console` and `browser_network_requests` return
"_No matching … captured yet._" for a tab that is generating traffic. `Page.loadEventFired` /
`Page.frameNavigated` also stop, so `pageInfoDirty` is never set and `client.pageInfo()` serves
the 1-second-TTL cache without invalidation. `Page.javascriptDialogOpening` stops too, so a
dialog on the re-visited tab is never captured and `browser_page_info` cannot warn about it.

**Impact** Silent, permanent-for-that-tab loss of all diagnostic data, plus a missed dialog
(which blocks every subsequent interaction with no explanation). The tool descriptions promise
the opposite: *"Buffer is reset on tab switch"* implies collection resumes after a switch.

**Severity** wrong result (silent data loss) — with a plausible path to a hard hang via the
missed dialog.

**Proposed fix.** Call `enableDomains(attachedSessionId)` unconditionally in `switchTo`, for the
`existing` branch as well. Re-enabling an already-enabled domain is a no-op in CDP, so hoisting
the call above the if/else is safe and simplest.

**Observable behaviour change.** Yes — events resume; up to six extra CDP round-trips per
re-visit (the `TODO(perf)` at `:207` already notes these are sequential).

**Reproducible in a test?** Yes, cleanly, with the existing stub transport: `switchTo("a")`,
`switchTo("b")`, `switchTo("a")`, then assert `calls` contains `Log.enable` for the third
`sessionId`. This is the single easiest finding in the report to pin down.

**Confidence.** High on the code shape. The premise "a second `attachToTarget` mints a new
sessionId and domain state is per-session" is standard CDP behaviour and is asserted by the
code's own comment, but I did not confirm it against a live browser.

## F4 — The event loop discards every event from non-active tabs, defeating the per-tab buffers

> **FIXED** in `7c6b3fd`. Handled with the extra care the ruling asked for: before
> widening the filter I traced every `switch` arm against a background-tab event.
> Three arms needed to change together, and widening the filter alone would have
> introduced a new bug —
> - `Page.javascriptDialogOpening` used the *active* `targetId`, so a background
>   tab's dialog would have been recorded against the foreground tab and
>   `browser_page_info` would have pointed the agent at the wrong tab. Now
>   `resolveTab(ev.sessionId)`.
> - `Page.frameNavigated` / `loadEventFired` had the same shape: the wrong tab's
>   page-info cache invalidated and the right tab's left stale. Now `resolveTab`.
> - `Target.targetCreated` / `targetDestroyed` are browser-level with no sessionId,
>   so they are unaffected either way; the `targetDestroyed` exemption was kept.
> - The `Network.*` / console arms already used `resolveTab` and simply start
>   receiving events.
>
> One ordering hazard the widening exposed: with the filter keyed on
> `sessionIdToTargetId`, events arriving during the six domain-enable round trips
> would have been dropped as "unknown", so tab registration moved ahead of
> `enableDomains` in both `attachFirstPage` and `switchTo`.
> Tests: `test/cdp/session-events-test.ts` — four failed first (console, network,
> dialog and load events from a background tab all discarded); the fifth, asserting
> that a session this instance never attached is still ignored, passed before and
> after and is the guard that the filter did not become a free-for-all.
> No design decision turned out to be needed, so I did not stop.

**Location** `src/cdp/session.ts:88-94`.

```ts
if (ev.method !== "Target.targetDestroyed") {
  if (ev.sessionId && ev.sessionId !== sessionId) continue;
}
```

**What breaks.** `sessionId` is the *active* tab's session. Every other attached tab's events are
dropped at the top of the loop. Yet the same loop then routes through
`resolveTab(ev.sessionId)` (`:151-178`), and `TabSession` carries a per-tab `networkBuffer` and
`consoleBuffer` explicitly so that *"switching tabs preserves the previous tab's data in its
TabSession instead of clearing it"* (`:13-16`). Those two designs contradict each other: the
per-tab buffers can only ever hold data captured while their tab was the active one.

Tabs stay attached after a switch (`tabs` and `sessionIdToTargetId` are never pruned on switch),
and `browser_open_urls` / `browser_read_page` attach extra sessions of their own, so there is
real traffic being thrown away.

**Trigger.** Switch to tab B while tab A is loading; switch back to A; call `browser_console` or
`browser_network_requests`. Everything A logged or fetched while B was active is absent, with no
`bufferOverflowed` flag or any other signal that data is missing.

**Impact** wrong result. Silently incomplete diagnostics — the failure mode the console and
network tools exist to prevent. Note this **masks F3**: with the filter in place, the missing
domain-enable on a revisit is partly invisible, and fixing either one alone gives a partial fix.

**Severity** wrong result (silent data loss).

**Proposed fix.** Narrow the filter to what it is actually for. Keep dropping events for
sessions this `CdpSession` does not know (`!sessionIdToTargetId.has(ev.sessionId)`), and let
known sessions through to `resolveTab`. Then move the three handlers that use
`targetId ? tabs.get(targetId)` (`javascriptDialogOpening` at `:97`, `frameNavigated` /
`loadEventFired` at `:117`) onto `resolveTab(ev.sessionId)` too, or a background tab's dialog
will be recorded against the foreground tab.

**Observable behaviour change.** Yes — background tabs accumulate console/network records, and
a background tab's dialog is attributed to the right tab.

**Reproducible in a test?** Yes. The stub transport's `events()` is a generator; replace it with
a pushable queue, `switchTo("a")`, `switchTo("b")`, push a `Runtime.consoleAPICalled` carrying
tab A's sessionId, `switchTo("a")`, assert `drainConsoleBuffer` returns it.

## F5 — `browser_fill` on a checkbox sets `value`, not `checked`, and reports success

> **FIXED** in `16e7a30`, together with F10 — one engine in
> `src/domains/fill-engine.ts`, used by both tools. A checkbox now goes through the
> click/`checked` path instead of the `value` setter.
> Tests: `test/domains/fill-engine-test.ts` executes the real in-page engine source
> in Node against fake DOM elements — the "pure branch-decision seam" this report
> recommended. 9 of its 16 assertions failed first, including the headline one:
> after `browser_fill(checkbox, "true")`, `checked` was still `false`.

**Location** `src/domains/form.ts:90-105` (`FILL_FN`).

*Pre-confirmed item — verified, and I agree it is the worst row of the two-engines table.*

**What breaks.** `FILL_FN` branches on `el instanceof HTMLInputElement` and, for any input,
fires `HTMLInputElement.prototype.value`'s setter. For `type="checkbox"` / `type="radio"` that
writes the element's *`value` attribute* — the string submitted when the box is ticked — and
leaves `checked` untouched. It then dispatches `input` + `change` (so a framework listener runs
and reads the *unchanged* checked state) and returns
`{ status: "ok", kind: "checkbox", value: el.value }`, which the handler renders as
`` Filled e7 = "true" ``.

**Trigger.** `browser_fill({ ref: <a checkbox>, value: "true" })`. There is nothing in the tool
description or `promptGuidelines` steering the agent away from it — `browser_fill` is
described as the field-filling default, and `browser_snapshot` gives checkboxes refs like every
other interactive element.

**Impact** A **silent no-op reported as success**, plus corruption of the checkbox's submit
value. The agent reads `Filled e7 = "true"`, believes the box is ticked, and moves on. The
appended `interactiveDiff` does compare `state`, so a careful reader might notice no
`checked` transition — but the primary result line says success.

**Severity** wrong result — the most damaging failure mode in the report, because it is silent
and the agent has no reason to doubt it.

**Proposed fix.** Add a checkbox/radio branch to `FILL_FN` that either delegates to the
`CHECK_FN` logic (`form.ts:379-394`, which clicks and falls back to `el.checked = want`) or
returns `{ status: "not_fillable", tag }` with a message pointing at `browser_set_checked`.
Failing loudly is strictly better than the current silence; delegating is better still, since
`browser_fill_form` already accepts a boolean for the same element (F10).

**Observable behaviour change.** Yes, and deliberately: a call that reported success now either
works or errors.

**Reproducible in a test?** The JS body is a string with no direct unit-test seam. Two options:
(a) reproduce in `test/manual/forms-test.ts` against live Chrome — proves it, doesn't guard it;
(b) restructure so the branch decision is a pure function of `{ tag, type, isContentEditable }`
and unit-test that. I recommend (b) — it is the only way this class of bug stays fixed, and it
covers F7 in the same seam.

## F6 — Every mutation silently renumbers the ref map, so refs held by the agent can point at different elements

> **FIXED** in `fe90a9c`. `interactiveDiff` now carries each ref over by
> `backendNodeId` (via a new `session.refMappings()`) and only mints a new `eN` for an
> element it has not seen; the counter starts above every existing number so a new
> element can never take a live ref.
>
> **Does this make refs genuinely stable, or narrow the window?** The ruling asked for
> an explicit answer. **Genuinely stable for any element that persists across the
> mutation** — which is the case the contract is about and the case that was silently
> wrong. Two honest residuals:
> - An element that disappears and later returns gets a **new** ref, because its old
>   ref is dropped from the map when it vanishes. The agent sees it as new (`*[eN]`),
>   which is truthful.
> - `browser_snapshot` still renumbers from scratch, by design: an explicit
>   re-snapshot is the documented way to get a fresh ref set.
>
> So the F6 divergence between `browser_snapshot`'s `interestingOnly`/`maxNodes` and
> `interactiveDiff`'s hardcoded values no longer *renumbers* anything — a node absent
> from the diff's narrower tree simply keeps no ref until the next snapshot.
> Tests: `test/domains/ref-stability-test.ts`. Two of four failed first, with `e1`
> resolving to backendNodeId 999 (the newly inserted element) instead of 101.
> While writing them I found my own first fixture was wrong, not the product: real
> CDP AX nodes carry `parentId`, and without it `buildTree` treats every child as an
> additional root and collects it twice. Fixture corrected; no product bug there.

**Location** `src/domains/ref-resolve.ts:75-94` (`interactiveDiff`), called from
`form.ts:160` (fill), `form.ts:307` (select), `click.ts:83` (click).
Compare `src/domains/snapshot.ts:332-344,371-376`.

**What breaks.** After each mutation, `interactiveDiff` re-reads the AX tree, re-runs
`collectInteractiveTargets`, and assigns refs by **positional index** — `e1, e2, …` in tree
order — then calls `session.setRefMap(refMap, refSig)`, replacing the map wholesale. If the
mutation changed the interactive element set (an error message with a link appears, a
conditional field renders, a button unmounts), every ref at or after the insertion point now
resolves to a **different element**. Not stale — *wrong*. `resolveRefToObjectId` cannot detect
this: it looks up `e6`, gets a live `backendNodeId`, resolves it, and fills the wrong field.

There is a second, independent divergence: `browser_snapshot` builds the tree with the
caller's `args.interestingOnly` / `args.maxNodes`, while `interactiveDiff` hardcodes
`{ interestingOnly: true, maxNodes: 1000 }`. A snapshot taken with `interestingOnly: false` or
`maxNodes: 5000` produces a *different numbering*, which the first mutation then replaces —
so refs shift even when the DOM did not change at all.

**Trigger.** The documented happy path in the system prompt (`src/prompt.ts:64-72`):
snapshot once, then `browser_fill(e7)`, `browser_select_option(e9)`, `browser_click(e12)`.
Any validation message or conditional field appearing after the first fill shifts `e9` and
`e12`. Reproducible deterministically with `browser_snapshot({ interestingOnly: false })`
followed by any fill.

**Impact** wrong result, silent, and it contradicts the contract the prompt and all seven tool
descriptions state: *"refs survive re-renders"*, *"refs are keyed to element identity"*.
What actually survives is the *backendNodeId behind a ref*, not the ref's meaning.

**Severity** wrong result. High: it targets the wrong element while reporting success, and it
sits directly on the recommended workflow.

**Proposed fix.** Make refs identity-keyed rather than positional. Keep a per-tab
`backendNodeId → ref` table and, when re-publishing in `interactiveDiff`, reuse the existing
ref for any backendNodeId already known, minting `eN` only for genuinely new nodes. That
preserves the diff (which already keys on `role|name`) and makes the "refs survive" claim true.
Minimum viable alternative: have `interactiveDiff` *not* replace the map — only add newly
appeared nodes — and use the same `buildTree` options the last snapshot used.

**Observable behaviour change.** Yes — ref numbers stay stable across mutations, and the
`*[eN]` markers in the diff change to reflect stable numbering.

**Reproducible in a test?** Yes, at the pure level and without a browser:
`buildTree(fixtureA)` → `collectInteractiveTargets` → refs; `buildTree(fixtureB)` where B is A
plus one interactive node near the top → assert the trailing refs still map to the same
`backendDOMNodeId`s. `test/deep-research/` already keeps AX-shaped JSON fixtures, so the
pattern exists.

## F7 — `browser_fill` and `browser_select_option` write through a **disabled** control and report `status: "ok"`

**Location** `src/domains/form.ts:90-122` (`FILL_FN`), `:254-268` (`SELECT_FN`).

**Trigger.** `browser_fill` on a field the form disables until a precondition is met — a "Submit"

**Severity** wrong result.

**Proposed fix.** Add `if (el.disabled) return { status: "not_fillable", tag }` — or a dedicated
`{ status: "disabled" }` so the message can say *why* — to both bodies, matching
`form-batch.ts:10` and `CHECK_FN` (`form.ts:385`), which both already do this.

**Observable behaviour change.** Yes: a previously "successful" write now errors. That is the
point, and it is the behaviour `browser_fill_form` already has.

**Reproducible in a test?** Same seam as F5 — pure branch-decision function, or live Chrome.

## F8 — `browser_fill` reports `verified` without ever comparing it to the requested value

**Location** `src/domains/form.ts:160-164`.

*Pre-confirmed item — verified, and I rate it lower than the pre-confirmed list implies.*

**What breaks.** The handler returns `details: { value: args.value, verified: res.value }` and
text `` Filled ${target} = ${JSON.stringify(res.value)} ``. `res.value` is `el.value` read back
after the write, but nothing compares it to `args.value`, and no mismatch is flagged. The tool
description promises *"Returns the field's value after writing, plus a compact diff"* — literally
true — while `promptGuidelines` says *"confirm both match what you intended"*, i.e. it delegates
verification to the agent's own reading of a string.

**Trigger.** Any input that transforms its value: `<input type="number">` given `"abc"` (becomes
`""`), a masked phone input, `maxlength` truncation, an `<input type="date">` given a
non-ISO string, or a controlled component that rejects and reverts.

attentive agent can catch it. `browser_fill_form` computes an explicit `mismatch` flag

## F11 — Concurrent liveness probes can spawn a second daemon that unlinks the live one's socket

**Location** `src/daemon/spawn.ts:41-101` (`isDaemonRunning`), `src/daemon/server.ts:83-89`
(`unlinkSync`), `:121-135` (duplicate-clientId rejection),
`src/daemon/protocol.ts:165` (`DAEMON_STALE_SOCKET_CLEANUP = true`).

**What breaks.** Three facts compose into a bad outcome:

1. `isDaemonRunning` registers with the **fixed** clientId `"_liveness_probe"` (`spawn.ts:70`).
2. `server.ts:126-134` rejects a registration whose clientId is already connected — it writes a
   `shutdown` control and destroys the socket.
3. On rejection the probe's `close` handler fires `done(false)` (`spawn.ts:96-99`), so
   `isDaemonRunning` reports **"not running"** for a daemon that is running and healthy.
   `ensureDaemon` then spawns a second daemon, whose `start()` unconditionally
   `unlinkSync(DAEMON_SOCKET_PATH)` (`server.ts:83-89`) — deleting the *live* daemon's socket
   inode — and listens on a fresh one.

The `close` handler's comment says *"daemon alive but rejected us (e.g. max clients); don't
unlink"* — so the author anticipated rejection, but the return value still says "not running",
which is what drives the spawn.

**Trigger.** Two pi sessions calling `/browser-setup` (or `browser_setup`, or any first tool
call) within the ~2 s probe window. The `_liveness_probe` slot is also never freed on the
reject path, so a probe that races itself in one process can do it too.

**Impact** Two daemons, two WebSockets to Chrome, two "Allow Remote Debugging" prompts — the
exact thing the daemon exists to eliminate. Sessions already connected keep working (their FD
survives the unlink), so the split is invisible until the user is prompted again. The orphaned
daemon lingers until its 30-minute idle timeout, if it ever reaches zero clients.

**Severity** resource leak, with user-visible fallout (repeat Chrome prompts).

**Proposed fix.** Two independent parts:
- Make the probe clientId unique: `` `_liveness_probe-${randomUUID()}` ``. Removes the collision
  entirely and costs nothing.
- Distinguish "rejected by a live daemon" from "nothing listening". A received `shutdown`
  control means the daemon is alive — `isDaemonRunning` should return `true`. And gate
  `unlinkSync` on the socket not being live rather than doing it unconditionally.

**Observable behaviour change.** No, in the normal single-session path. In the race, one daemon
instead of two.

**Reproducible in a test?** Yes — `test/manual/ipc-server-test.ts` and
`live-daemon-test.ts` already drive the real server over a real socket. A test that registers
`_liveness_probe` and then calls `isDaemonRunning()` and asserts `true` is straightforward.
It lands in `test/manual/`, which the `npm test` glob excludes, so it would not run in CI
without the daemon-test infrastructure F30 asks for.

## F13 — A `session_tree` event before client creation resets the namespace to `"default"`

**Location** `src/index.ts:195-198`; `src/state.ts:51-68` (`restoreState`).

*Pre-confirmed item, flagged "confirm whether the fallback makes these equivalent". It does
not, in one specific case.*

**What breaks.** `session_tree` passes `client?.namespace`, which is `undefined` before the
client exists (the client is created in `session_start`). Inside `restoreState`:

```ts
const fallback = defaultState(currentNamespace);   // namespace = undefined ?? "default"
…
namespace: currentNamespace ?? data.namespace ?? fallback.namespace
```

With a persisted entry present, `data.namespace` wins and the two call sites *are* equivalent.
With **no** persisted entry, the loop falls through to `return fallback` — whose namespace is
`"default"`, not the `pi-<random>` value `index.ts:40` generated. `persistState` then writes
`"default"`, and the subsequent `session_start` reads it back and creates the client (and the
daemon transport) with `namespace: "default"`.

**Trigger.** A `session_tree` event arriving before `session_start` in a session with no prior
`browser-harness-state` entry — a fresh session on a fresh branch. Whether pi actually orders
the events that way I could not determine from this repo; the ordering is the host's.

**Impact** Every affected pi session shares the daemon clientId `"default"`, so the second one
to connect is rejected by `server.ts:126-134` ("clientId default is already connected") and
gets its socket destroyed. Multi-session browser control breaks, and the error surfaces as a
generic transport failure. If `--browser-namespace` was passed, `flagNs` is not consulted here
either, so an explicit user choice is discarded.

**Severity** wrong result (conditional on host event ordering; **unverified** that the ordering
occurs).

**Proposed fix.** Pass the namespace that is authoritative, not the one that happens to be
reachable: `restoreState(ctx, client?.namespace ?? state.namespace)`. `state.namespace` is
initialised from the flag or the generated value at `:40-42`, so it is never `undefined` — which
also makes the two call sites genuinely equivalent and removes the trap.

**Observable behaviour change.** None in the ordering where `session_start` runs first. In the
other ordering, the namespace stops being clobbered.

**Reproducible in a test?** Yes, and cheaply — `restoreState` takes only an `ExtensionContext`
whose `sessionManager.getBranch()` returns an array. A test asserting
`restoreState(ctxWithNoEntries, undefined).namespace` is not silently `"default"` when the
caller had a real namespace pins the contract. Reproducing the *event ordering* needs a pi
host fake, which does not exist here.

## F14 — Both `AbortController` time budgets are dead code: the pre-`await` check can never fire

**Location** `src/domains/snapshot.ts:346-366` (1 500 ms box budget) and
`src/domains/network.ts:249-266` (5 000 ms `BODY_BUDGET_MS`).

*This is the "signal.aborted checked before an await, not re-checked after" item from the
brief's list — present in two places, in a slightly worse form than described.*

**What breaks.** Both sites build the whole array of promises with `.map(async …)` and then
await them together. `.map` starts every async function **synchronously**, so the guard at the
top of each callback runs before the timer can possibly have fired:

```ts
const timer = setTimeout(() => ac.abort(), BODY_BUDGET_MS);
const fills = drained.records.map(async (r) => {
  if (ac.signal.aborted) return;                  // always false — same tick
  const bodyRes = await session.call("Network.getResponseBody", …);   // never re-checked
  …
});
await Promise.allSettled(fills);
```

`session.call` takes no `AbortSignal`, so aborting cannot cancel an in-flight request either.
Net effect in `network.ts`: the 5 s budget bounds nothing at all — all N `getResponseBody`
calls are issued, and the tool waits for every one (each up to the 15 s transport timeout).
In `snapshot.ts` the *first* check is likewise dead, so no `DOM.getBoxModel` is ever skipped;
only the **second** check (`:360`, after the `boxOf` await) does anything, and it only skips the
`liveValue` follow-up.

**Trigger.** `browser_network_requests({ includeResponseBodies: true })` matching many records
on a slow page. `browser_snapshot` on a page with many interactive elements.

**Impact** wrong result via latency: a tool documented as budgeted can block far past its
budget, and the caller sees a plain timeout with no partial data. Not a crash; nothing is
mis-stated in the output.

**Severity** wrong result (latency/robustness). Low-to-medium.

**Proposed fix.** Bound the whole batch instead of guarding inside each task:
`await Promise.race([Promise.allSettled(tasks), sleep(BUDGET_MS)])`, and record per-record
completion so partial results are reported honestly. If per-task cancellation is wanted, thread
a `timeoutMs` (already supported by `session.call`) derived from the remaining budget —
`src/util/time.ts` already exports a `deadline()` helper built for exactly this and currently
has no callers in `src/`.

**Observable behaviour change.** Yes — the tool returns within its budget with partial bodies
instead of eventually returning all of them.

**Reproducible in a test?** Yes for `network.ts`, with a fake client whose
`session().call("Network.getResponseBody")` resolves after a controllable delay: assert the
handler returns within ~`BODY_BUDGET_MS` for 50 records at 200 ms each. Needs the same
`makeFakeClient()` helper as F2/F9.

is not affected — the three wait tools use three different sleep strategies.

**Trigger.** Cancelling `browser_wait_for` (Esc / agent cancellation) within a 50 ms window.

**Impact** A thrown exception instead of the `{ kind: "internal", message: "aborted" }` the

**Severity** cosmetic.

**Proposed fix.** Wrap the loop body, or make the three wait tools share one abortable-sleep
helper that returns a `Result` rather than throwing. The blanket handler try/catch from F19

**Observable behaviour change.** Yes — a typed error on cancellation.

**Reproducible in a test?** Yes — `sleep` is pure and needs no client; the handler needs a fake

## F21 — `openIsolatedTab` can adopt and then close the harness window's only tab

**Location** `src/domains/isolated-tab.ts:35-63` and `:112-114` (`closeIsolatedTab`);
`src/cdp/target-factory.ts:144-182`.

**What breaks.** When `ensureHarnessWindow` reports `freshlyCreated: true`,
`openIsolatedTab` uses the **seed tab of the newly created harness window** as its isolated tab.
`ensureHarnessWindow` has, by then, recorded that same target as `harnessWindow` and added it to
ownership. `closeIsolatedTab` closes it in the `finally`, so the window that was just
established is destroyed and the window binding is dropped (`ownership.remove` clears
`harnessWindow` when the ids match, `ownership.ts:54-57`).

**Trigger.** `browser_web_search` or `browser_read_page({ url })` at a moment when no owned tab
is live. `ensureAlive` normally runs first and seeds a window, so the window usually already
exists and `freshlyCreated` is false — the exposure is the narrow window where the user closes
the harness tabs between `ensureAlive` and the isolated-tab call. Also reachable when the
concurrency coordinator hands `freshlyCreated: true` to the creating caller while a second
concurrent `browser_read_page` is in flight.

**Impact** With a pinned profile, the next tool call re-runs `seedPinnedProfileWindow`, which
**launches a browser window via the command line** — visible, slow (up to 15 s of sentinel
polling), and disruptive. If the session was attached to that seed tab, the next call also gets
`session_not_found` and re-attaches. It contradicts the tool's documented promise:
*"Runs in its own isolated tab and never disturbs the user's current tab."*

**Severity** resource leak / lifecycle churn (no wrong data).

**Proposed fix.** Never let an isolated tab *be* the harness window's seed tab: after
`ensureHarnessWindow` returns `freshlyCreated: true`, still call `openHarnessTab` to get a
sibling, and leave the seed alone. That is a two-line change and makes the seed tab's role
(a durable window anchor) consistent across all callers.

**Observable behaviour change.** One extra tab open+close per isolated read in the fresh-window
case; the harness window survives.

**Reproducible in a test?** Only with a fake client that can report "no owned tabs" and record
`Target.closeTarget` calls. Fiddly but doable; the race variant is not deterministically
reproducible. **Partly unverified** — I traced it in the code but did not observe it.

## F22 — The daemon never releases session ownership on `Target.detachFromTarget`

**Location** `src/daemon/bridge.ts:386-391`; caller `src/client.ts:375-383`.

**What breaks.** The bridge does `if (isDetach && req.sessionId) router.release(req.sessionId)`.
But `client.detach()` sends `Target.detachFromTarget` with the session id in **`params`**, at
browser level (`{ sessionId: null }` transport option), so `req.sessionId` on the envelope is
`undefined` and the release never runs. `EventRouter.owners` keeps the mapping for a session
that no longer exists.

**Trigger.** `session_shutdown` (which calls `client.detach()`), every session, every time.

**Impact** A slow leak in a long-lived daemon: `owners` grows by one entry per detached session
and is only pruned by an `Inspector.detached` event (`bridge.ts:199-201`) or `removeClient` on
disconnect. Since the transport deliberately survives session shutdown
(`index.ts:184-187`), `removeClient` does not fire. Events for a dead session would also still
be routed to the stale owner — harmless, since Chrome stops sending them.

**Severity** resource leak (small, bounded by daemon lifetime and the 30-minute idle exit).

**Proposed fix.** Read the id from either place:
`const sid = req.sessionId ?? asString(req.params?.["sessionId"])`. `asString` is already
imported in `bridge.ts`.

**Observable behaviour change.** None observable; the map shrinks.

**Reproducible in a test?** Yes — `handleRequest` is a plain function taking a `WireRequest`
and a `send` callback; `getSessionOwner` is exported for the assertion. It lands in
`test/manual/bridge-test.ts`, outside the CI glob (F30).

## F23 — `handleRequest`'s promise is dropped with no `.catch`

**Location** `src/daemon/index.ts:24-32`.

**What breaks.** `cdpBridge.handleRequest(msg, client.id, send)` returns a `Promise<void>` that
is neither awaited nor `.catch`-ed, inside a `readline` `"line"` handler. Any rejection is an
unhandled rejection, which on Node ≥ 15 terminates the process by default — taking the daemon,
and every connected pi session's browser control, with it.

**Trigger.** No reachable throw found. `handleRequest`'s only `await` is a `setTimeout` sleep;
`JSON.stringify(payload)` and `ws.send` are inside a try/catch; `mux.allocate` cannot throw.
A future edit that adds an unguarded `await` in that function makes it reachable.

**Impact** None today. This is the same latent shape as the `bridge.ts:156` `JSON.parse` bug
that Task 4 fixed — an unguarded failure path inside a socket handler with nothing above it —
and it sits in the same file's blast radius.

**Severity** cosmetic today, crash-class if a throw is ever introduced.

**Proposed fix.** `void cdpBridge.handleRequest(msg, client.id, send).catch((e) => { … send an
error response … });` — or make it explicit with `process.on("unhandledRejection")` logging in
the daemon entry point. Cheap insurance for a process whose whole job is to stay up.

**Reproducible in a test?** Yes at the seam — inject a bridge whose `handleRequest` rejects and
assert the process/handler survives. Needs the daemon test infrastructure from F30.

## F24 — `interactiveDiff` keys the diff on `role|name`, so duplicate-named elements collapse

**Location** `src/domains/ref-resolve.ts:96-126`.

**What breaks.** The diff builds `prevByKey` / `curByKey` maps keyed on `` `${role}|${name}` ``.
Any two interactive elements sharing a role and an accessible name overwrite each other, so only
the last one is compared. The comment explains the choice (*"Compare by stable identity
(role|name) rather than ref position, since refs renumber"*) — which is itself the symptom of F6.

**Trigger.** Very common: a table with a "Delete" button per row; several unlabelled textboxes
(all `textbox|`); repeated "Add to cart" buttons.

**Impact** The "Page changes" block under-reports. A value change on row 3's field can be
attributed to row 7's, or dropped. Since the whole point of the diff is *"read it to confirm the
change landed"* (`prompt.ts:30-31`), an agent trusting it can be misled — but the primary result
line (`Filled e7 = "…"`) is still correct, so nothing depends solely on the diff.

**Severity** cosmetic (misleading advisory output).

**Proposed fix.** Falls out of F6's fix for free. With identity-stable refs, key the diff on
`backendNodeId` and the collapse disappears. Not worth fixing independently.

**Reproducible in a test?** Yes, pure, from two AX fixtures with duplicate `role|name` pairs.

## F25 — `limit: 0` would make both buffers return everything (investigated — not a live bug)

**Location** `src/cdp/console-buffer.ts:227-228`, `src/cdp/network-buffer.ts:174-175`.

```ts
const limit = Math.min(filter.limit ?? 50, 500);
const limited = matched.slice(-limit);
```

With `limit === 0`, `-0` is `0` and `matched.slice(0)` returns the **entire** array — the exact
opposite of "return nothing".

**Why it is not a live bug.** Both tool schemas set `minimum: 1` on `limit`
(`console.ts:35`, `network.ts:80`), so a validated `0` cannot arrive. `drainConsoleBuffer` /
`drainNetworkBuffer` have no other callers in `src/`.

**Note for the record.** This is a **guard made dead by a schema constraint** — the category the
brief flags. Here the guard is fine and the schema is right; the fragility is that the buffer's
own contract does not hold without the schema. If the buffers are ever reused (a script via
`browser_run_script` gets `daemon` = the full `BrowserClient` and can reach
`client.session().drainConsoleBuffer({ limit: 0 })` **today**), it fires.

**Severity** cosmetic (latent; reachable only via `browser_run_script`).

**Proposed fix.** One line in each: `if (limit <= 0) return { records: [], total, bufferOverflowed }`
— or `matched.slice(Math.max(0, matched.length - limit))`.

**Reproducible in a test?** Yes, trivially — both buffers are pure and dependency-free, and
this is a 5-line test. Worth doing purely because it is so cheap.

## F27 — The boundary scanner has no rule for `: any`

**Location** `scripts/check-boundaries.ts:13-19` (`RULES`).

*Pre-confirmed item — verified, including the false-positive hazard.* The five rules cover
`as any`, `@ts-ignore`/`expect-error`/`nocheck`, non-null assertions, `as {`, and
`as unknown as`. Nothing covers a bare annotation: `const x: any = …`, `(p: any) => …`,
`Promise<any>`.

`src/` has no `: any` today, so nothing is broken — but the whole point of the scanner is that
the property cannot silently regress, and this one can.

**The false-positive hazard is real.** A naive `/:\s*any\b/` matches the long prose
`description` strings throughout `src/domains/` — e.g. `snapshot.ts:296`
(*"or (b) browser_snapshot and browser_execute_js cannot answer your question"* is safe, but
`js.ts:48` contains *"is this element visible / enabled / checked / focused"* and
`network.ts:74`'s resource-type list and several `promptGuidelines` lines contain `any` after a
colon in ordinary English). Anchoring on a terminator is required.

**Severity** cosmetic (process guard rail).

**Proposed fix.** Add `{ rule: "any-annotation", re: /:\s*any\s*(?:[=;,)\]>|&]|$)/ }` — a colon,
`any`, then a type-position terminator. Verify against the current tree: the rule must report
zero violations on `src/` as it stands. `test/util/check-boundaries-test.ts` already exists and
`checkSource` takes injected files, so both the positive and negative cases are directly
testable.

**Observable behaviour change.** None to runtime; `npm run boundaries` gains a rule.

## F28 — `sharp-shim.ts`'s indirection has invisible intent and invites a breaking "simplification"

**Location** `src/util/sharp-shim.ts:23,34`.

*Pre-confirmed item — verified. Functionally correct; a maintenance trap.*

`const SHARP_SPECIFIER: string = "sharp";` followed by `await import(SHARP_SPECIFIER)` exists so
TypeScript cannot statically resolve the specifier and therefore does not require `sharp`'s
types — which is what removed the `@ts-ignore`. Nothing in the file says so. The explicit
`: string` annotation (redundant on a string literal) is the entire mechanism: it widens the
literal type so the import is dynamic to the compiler.

A reader applying an "inline the constant" cleanup — plausibly Task 17, which strips comments —
restores a statically-resolvable `await import("sharp")` and breaks the build in any workspace
where the optional dependency is absent.

**Severity** cosmetic (maintainability).

**Proposed fix.** This is the one place in the file that needs a comment to survive Task 17.
Alternatively make the intent structural and self-evident:
`const specifier = ["sh", "arp"].join("")` is worse; a named export
`const OPTIONAL_SHARP_SPECIFIER` plus one line of explanation is the honest answer. Flag it as
comment-exempt for Task 17 either way.

**Reproducible in a test?** Partly. A test asserting `loadSharp()` returns `{ kind: "missing" }`
rather than throwing when `sharp` is absent guards the runtime behaviour, but nothing can
prevent the compile-time regression except the comment.

## F29 — Ref-based fill/focus/select leak a CDP object handle on every call

**Location** `src/domains/form.ts:30-45` (`runOnElement`, ref branch);
also `src/domains/keyboard.ts:152-165` (`browser_dispatch_key`, ref branch) and
`src/domains/snapshot.ts:263-281` (`liveValue`).

*Pre-confirmed item — verified, and it is in **three** places, not one.*

**What breaks.** `resolveRefToObjectId` produces a `Runtime.RemoteObject` handle via
`DOM.resolveNode`. Chrome retains that object (it cannot be GC'd) until
`Runtime.releaseObject` is called or the execution context is destroyed. `runOnElement` never
releases it. `resolveAndCall` in the same file **does** (`form.ts:369-371`, in a `finally`),
so the correct pattern already exists two hundred lines away, and `Runtime.releaseObject` is
already in the typed command table (`commands.ts:193`).

`liveValue` in `snapshot.ts` is the worst site by volume: it resolves one handle **per
interactive form control per snapshot** and releases none.

**Trigger.** Every `browser_fill`, `browser_focus`, `browser_select_option`, and
`browser_dispatch_key` on the ref path, plus every `browser_snapshot` (once per
`VALUE_ROLES` control).

**Impact** Renderer memory growth in the user's real browser tab, proportional to how long the
session runs. Released on navigation (context destroyed), so it is bounded per page. A
long-running SPA session doing hundreds of snapshots and fills is the bad case.

**Severity** resource leak.

**Proposed fix.** Wrap all three in `try { … } finally { await session.call("Runtime.releaseObject", { objectId }) }`,
exactly as `resolveAndCall` does. For `runOnElement` specifically, F2's suggested fix
(route the ref branch through `resolveAndCall`) fixes the leak and the missing
`exceptionDetails` check in one change.

**Observable behaviour change.** One extra CDP round-trip per ref operation; no user-visible
difference.

**Reproducible in a test?** Yes with a fake client that records calls: assert
`Runtime.releaseObject` appears after `Runtime.callFunctionOn`. Same missing `makeFakeClient()`
helper as F2.

## Investigated — not bugs

Recorded because the reasoning is worth as much as a finding.

**F31 — `spawn.ts` resolving the daemon entry as `index.ts`.** The comment at `spawn.ts:107-112`
says the entry is `dist/daemon/index.js` when running compiled, but the code only ever builds
`join(moduleDir, "index.ts")`. Checked `package.json`: `files` ships `src/` (no `dist/`) and
`pi.extensions` is `./src/index.ts`. The package runs from TypeScript source via `tsx` in every
distribution path, so the code is right and only the comment is stale.

**F32 — `picker.ts:61` mapping a selected label back to a profile by `options.indexOf`.** Looked
for an off-by-one or a collision: `rows[i]` is built from `labels[i]` which is built from
`profiles[i]`, and `CLEAR_SELECTION_LABEL` is appended last and handled before the `indexOf`.
`disambiguate` guarantees distinct labels, and the pinned row's `"✓ "` prefix keeps it distinct
from an unpinned duplicate. Correct.

**F33 — `restoreState`'s fallback making the two call sites equivalent.** They *are* equivalent
whenever a persisted entry exists. The non-equivalence is narrow and specific — see F13, which
is the real finding this investigation produced.

**F34 — `util/mutex.ts` and `util/result.ts`.** Read closely for a lost-release or a chain that
can reject. The mutex's queue is only ever advanced by `resolve`, `registerBrowserTool` releases
in a `finally`, and no handler holds the lock across a `return` without it. Correct.

**F35 — `console-buffer.clear()` resetting `nextSeq` to 1.** This would invalidate every
outstanding `nextCursor` (a stale cursor would suppress new records whose seq restarted below
it). Grepped: `clear()` has **no caller** in `src/`. Dead code, not a bug. Worth deleting or
making seq-monotonic if it is ever wired up.

**F36 — `bind.ts:111` `if (seed.browserContextId) client.setProfileContextId(...)`.** If a
sentinel page arrived without a `browserContextId`, `profileContextId()` stays undefined,
`canReuse` in `ensureHarnessWindowUncoordinated` stays `false` forever, and **every**
`ensureHarnessWindow` call would command-line-launch a new profile window. That would be severe.
But `TargetInfo.browserContextId` is populated for targets in a non-default browser context —
which a pinned non-default profile's window is by construction — and the launched window is
always non-default relative to the connected browser's default context. Classified **not a bug,
low residual risk**: if the pinned profile happens to *be* the browser's default context, the
field may be omitted and the degenerate loop becomes reachable. Unverified; a one-line
`else` returning a clear error would remove the doubt cheaply.

## Ranking: is `exceptionDetails` the most severe item?

**No — I put it fourth.** F2 is real and should be fixed, but its failure is *loud*: the agent
gets an error, the wrong error. It re-snapshots and retries. Nothing downstream is corrupted.

Above it I place three findings whose failure is **silent**:

2. **F5** — `browser_fill` on a checkbox reports success for a no-op. The agent proceeds on a

3. **F6** — refs renumber under the agent's feet, so a mutation can hit the wrong element while

findings in the report to reproduce and fix.

The ordering principle: **silence beats severity**. A wrong error message costs a retry; a false
